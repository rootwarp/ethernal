## [V4-1] `InMemoryPassphrase` + `loader` dep on `ValidatorDeps`

**Points:** 1 · **Depends on:** V3-1 · **Discharges:** PR-17, test seam for PR-19

**Description.** C4 calls `KeyLoader::load(path, &dyn PassphraseSource)`
(`keystore.rs:66`). Two pieces of plumbing are needed first: a passphrase source backed by the
buffer already in memory, and an injectable loader so the failure path is testable.

**Implementation notes.**

1. **`InMemoryPassphrase`** in `bins/ethernal/src/keystore_cli.rs` (D-6 — that module already
   hosts namespace-neutral keystore CLI helpers such as `write_with_retry`;
   `test_support::FixedPassphrase` is test-only and must not be promoted):
   ```rust
   /// A `PassphraseSource` over a passphrase already held in memory, for the
   /// post-write decrypt round trip (C4). Never prompts and never re-reads the
   /// environment: re-prompting mid-loop is unacceptable and a second `EnvSource`
   /// read is a needless extra exposure.
   pub(crate) struct InMemoryPassphrase(Zeroizing<Vec<u8>>);
   ```
   `read()` returns a fresh `Vec` copy — the trait returns a plain `Vec` and documents that the
   caller must re-wrap (`passphrase.rs:27`); `Loader::load` does. The master copy stays in
   `Zeroizing`.
2. **`ValidatorDeps.loader`** (`validator_cmd.rs:42`):
   ```rust
   /// EIP-2335 loader for the C4 round trip. Production: `&Loader`.
   pub loader: &'a (dyn KeyLoader + Sync),
   ```
   Precedent: `GenDeps.loader` has exactly this type (`gen_cmd.rs:56`). Wire `&Loader::new()`
   in both production entries (`run_validator_new` `:112`, `run_validator_recover` `:165`) and
   add the field to every existing test constructor.
3. `summary_out: &'a mut dyn Write` is **unchanged** (D-2) — that is the seam the spinner-thread
   design would have broken, and nothing here needs it.

**Acceptance criteria.**
- [x] `InMemoryPassphrase::read()` returns the exact bytes; two calls return equal, *separate*
      allocations (unit test).
- [x] `ValidatorDeps` has `loader`; both production entries pass a real `Loader`; every
      existing test constructor compiles with one added field initializer and **no assertion
      changed**.
- [x] `make lint && make test` green.

**Out of scope.** No C4 call yet (V4-2). No flag (V4-3).

## [V4-2] `verify_written_keystore` (C4) + `verifying` phase

**Points:** 2 · **Depends on:** V4-1 · **Discharges:** PR-13, PR-15, PR-19

**Description.** After `write_keystore_at` returns a path, read **that file** back through the
loader and assert both halves of its identity.

**Implementation notes.**

- Assert **both**:
  1. `key.secret == sk_bytes` (constant-time compare preferred; the values are ours, but the
     habit is cheap)
  2. `key.pubkey_hex == pubkey_hex`
- (2) is the non-obvious half and the strongest single justification for the feature:
  `KeyLoader` explicitly does **not** validate that the JSON `pubkey` matches the ciphertext
  ("the loader does not validate its length or that it matches `Key::secret`",
  `keystore.rs:29`), and `deposit gen` indexes keystores by that field via `scan_dir` **without
  decrypting**. A keystore whose `pubkey` disagrees with its ciphertext is therefore accepted
  by every later stage of this tool's own pipeline. C4 makes that unrepresentable at creation.
- Read the **file**, never the in-memory `json` buffer (PR-13) — the check exists to catch a
  bad write, not to re-check arithmetic.
- `Key` zeroizes on drop (`keystore.rs:50`); still call `key.zeroize()` explicitly after the
  compare, matching the crate's stated convention.
- Emit `Phase::Verifying` immediately before the call.
- **Failure (PR-15, D-5):** leave the file, stop the run, exit 3. Message:
  ```
  keystore self-check failed for index {i} (C4): {detail}
    file: {path}
    the file was NOT removed; do not use it. No further keys were created.
  ```
  Do **not** unlink and do **not** rename. The write path is `create_new`-exclusive and never
  overwrites; deleting key material on the strength of the tool's own possibly-buggy check —
  or on a transient read error — is the one irreversible act in a pipeline designed to have
  none. The operator lands in a defined state: *k* verified keystores plus one named suspect.

**Acceptance criteria.**
- [x] Happy path `--count 2`: both keystores are decrypted back and compared; the run still
      writes exactly 2 files with unchanged content and permissions.
- [x] **Negative test (PR-19):** an injected `KeyLoader` returning a mismatched secret →
      `KeyVerifyFailed{check:"C4"}`, `exit_code_for` = 3, the run stops at that index, earlier
      keystores remain, **and the failing file still exists on disk** (assert the path).
- [x] Second negative test: loader returns the right secret but a mismatched `pubkey_hex` →
      same outcome. (This is the `scan_dir`-accepts-it case; it must fail loudly.)
- [x] No re-prompt / no second env read during the loop: a passphrase source that counts calls
      shows exactly one call to the *original* source for the whole run.
- [x] `[1/N] verifying` appears in a `Progress::Tty` buffer; nothing appears under `NonTty`.
- [x] Measure and record in the PR description: e2e suite wall-clock before vs. after
      (expect roughly ×2 on keystore-writing paths — project-plan §6 risk 1).
- [x] `make lint && make test` green; **no existing assertion modified**.

**Out of scope.** The flag (V4-3). Account/v3 parity (deferred).

## [V4-3] `--no-verify` flag, warning, and `verified=` log field

**Points:** 1 · **Depends on:** V4-2 · **Discharges:** PR-12, PR-18

**Description.** Give large-batch operators an escape hatch from C4's cost — and only C4's.

**Implementation notes.**

- `validator_cli.rs`: `--no-verify` on **both** `new` and `recover`. Help text must state the
  boundary explicitly:
  ```
  Skip the post-write keystore decrypt round-trip (C4). Derivation self-checks
  (C1-C3) always run and cannot be skipped. Halves wall-clock at the cost of the
  strongest correctness check.
  ```
- `ValidatorConfig` (`validator_cli.rs:32`) gains `pub verify_keystore: bool`, **default
  `true`**; the flag sets it to `false`. Positive naming so call sites read
  `if cfg.verify_keystore`.
- One stderr notice, once per run, before the loop:
  `WARNING: --no-verify — keystores will not be decrypted back after writing.`
  This is the only new `WARNING` line and cannot fire on the default path, so
  `tests/validator_e2e.rs:444` ("exactly one WARNING" on the symlink case) stays green (PR-9).
- `emit_key_progress`'s `NonTty` arm gains one k/v on the existing `keystore written` event
  (PR-18): `("verified", "full" | "derived-only")`. **No new event** — CI log volume is
  unchanged. The TTY line stays byte-identical (PR-4).

**Acceptance criteria.**
- [ ] `--no-verify` on a `--count 2` run: no decrypt happens (assert via a call-counting
      loader), C1–C3 still run (assert via the `checking` phase and a forced C1 failure still
      exiting 3), exactly one `WARNING` line.
- [ ] Default run (no flag): `verified=full` in the `NonTty` log event; with the flag,
      `verified=derived-only`.
- [ ] `validator new --help` and `validator recover --help` both show the flag with the
      C1–C3 caveat.
- [ ] `make lint && make test` green; **no existing assertion modified**.

**Out of scope.** No `--json-logs` for validator (deferred). No config-file or env form of the
flag.
