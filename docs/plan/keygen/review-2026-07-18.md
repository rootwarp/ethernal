## Medium

### M1 — `key recover` echoes an unknown mnemonic token to stderr and the logger
`crates/core/src/bip39.rs:19,103` → `bins/eth-deposit/src/key_cmd.rs:271` → `bins/eth-deposit/src/errors.rs:121` → `bins/eth-deposit/src/main.rs:134`

On `key recover`, the first mnemonic token that fails wordlist membership is embedded verbatim in `Bip39Error::UnknownWord(String)` (`bip39: unknown word {0:?}`) and rendered to stderr and the structured logger on the exit-2 path — the channel the S-2 secret-hygiene rule forbids for mnemonic material. Example: `printf '... wroth ...' | eth-deposit key recover ... 2> recover.log` leaves `err="bip39: unknown word \"wroth\""` in the log.

- Found independently by both the K1 and K3 reviewers (K1 rated Low, K3 Medium; Medium adopted since S-2 is a stated hard property and the gap is untested).
- Bounding: the token is by construction **not** a wordlist word, so only a typo/corruption token leaks (~11 bits of hint about one word), never a real secret word. `{0:?}` escapes control bytes (no terminal-escape injection).
- Root cause is a **spec/contract inconsistency, not a code slip**: the message format is specified in `docs/plan/keygen/architecture.md:80-84`, so the implementation faithfully follows an architecture that contradicts S-2 on the recover path. The K3-4 hygiene tests (`secret_hygiene_key_new_buffers` / `_recover_buffers`) only run valid mnemonics and never catch it.
- **Fix:** report the word's 1-based *position* instead of the token (or scrub `AppError::Bip39` at the `main.rs` log boundary); add a hygiene test that drives a `validate_mnemonic` failure and asserts the token is absent. Update `architecture.md` accordingly.

## K1 — Derivation primitives (commit `9ef24e5`)

**Verdict: PASS.** Cryptography sound; M-K1 gate satisfied (Trezor BIP-39 vectors incl. `abandon×23 art` + `TREZOR`, four official EIP-2333 vectors, wordlist sha256 pin `2f5eed53…`/13116 bytes, OS-CSPRNG-only entropy with no override outside test).

### Low
1. **Un-zeroized `indices: Vec<usize>` leaves a full copy of the master secret in freed heap** — `bip39.rs:57` (generate), `bip39.rs:99` (recover); secondary residue in the `Vec<&str>` join at `bip39.rs:78-82`. The 11-bit index vector is a bit-for-bit encoding of entropy+checksum, dropped without zeroization while sibling buffers are `Zeroizing`. Exploitation needs a local memory-disclosure primitive (core dump, swap, heap read), but it defeats the point of zeroizing everything else. *Top-priority K1 fix:* `Zeroizing::new(Vec::with_capacity(word_count))` for both vectors; build the mnemonic into a `Zeroizing<String>`. (Security-auditor rated Medium; held at Low on threat-model reachability.)
2. **`to_seed` silently lossy-decodes a non-UTF-8 mnemonic passphrase** — `bip39.rs:163`. Invalid UTF-8 is repaired with U+FFFD before NFKD, deriving a valid-looking but wrong seed with no error — a mis-encoded "25th word" means permanent loss (unrecoverable in any conformant wallet). Fail closed: error on invalid UTF-8. (Salt normalization is otherwise spec-correct: NFKD, not lowercased — the uppercase `TREZOR` vector passes.)
3. **`UnknownWord` token echo** — see M1 above (K1's instance of the same finding).
4. **SHA-256 digest of entropy and checksum bytes not zeroized** — `bip39.rs:54,133,135,112`. Weakest finding: SHA-256 is one-way, digest can only confirm a candidate an attacker already holds. Defense-in-depth only.

### Test-coverage note
The only negative checksum test (`validate_checksum_flip`, `bip39.rs:298`) covers cs_bits=4 (12-word) only. cs_bits=5–8 rejection — including the 24-word `key new` default — is currently correct (bit-math traced and empirically confirmed) but unguarded against regression. Add a 24-word checksum-flip test.

### Verified non-issues
MSB-first bit-math consistent across all 5 word counts, no off-by-one/overflow/panic on arbitrary input; `validate_mnemonic` and `to_seed` share identical normalization; wordlist pure-LF, pinned, duplicate-free; `hd.rs` fully delegates to blst (Result propagated, `Zeroizing` returns, no Debug on secret types, blst SecretKey self-zeroizes); `OsEntropy` (getrandom 0.3.4) sole production entropy, `FixedEntropy`/`CancelOnFill` are `#[cfg(test)]`-gated. Honest verification boundary (violates no criterion): 15/21-word checksum accept-paths rest on uniform bit-math + self-round-trip (Trezor set skips those sizes); full `derive_path` composition is pinned by constants + per-step vectors and E2E-gated downstream.

## K2 — Keystore creation (commits `f28756a`, `af8f521`, `a9820e5`)

**Verdict: PASS.** All acceptance criteria met: EIP-2335 scrypt spec vector byte-for-byte (injected salt/iv/uuid, non-ASCII NFKD password); Loader round-trip; wrong passphrase rejected; UUID-v4 bits correct with no `uuid` crate; `write_new_0600` atomic, 0600-before-bytes, refuse-overwrite, no tmp on handled errors; `NewKeystorePassphrase` confirm-twice + ≥8 on the normalized form. Diff-verified invariants: decrypt path behavior-preserving, `FsWriter`/`EnvSource`/`TermPromptSource` untouched.

### Low
1. **`write_new_0600` crash window leaves a 0-byte stub that blocks retry** — `crates/core/src/output.rs:283-302`. Refuse-overwrite is implemented by `create_new`-ing an empty file at the final path, then renaming the tmp over it; the `TmpGuard` owns only the tmp. A kill between the two leaves an empty 0600 file → next run gets `AlreadyExists` until an operator deletes the stub. Fail-safe (no secret in the stub) but an operator footgun. `renameat2(RENAME_NOREPLACE)` or link-then-unlink removes the window.
2. **No parent-directory fsync after rename** — `output.rs:291`. Power loss just after reported success can lose the file. Same gap as the pre-existing `FsWriter`; Low because the mnemonic is the true backup.
3. **Non-UTF-8 passphrase leaves an un-zeroized lossy copy** — `crates/keystore/src/crypto.rs:22`. Unreachable today (both production sources deliver valid UTF-8); wrap the lossy `into_owned()` in `Zeroizing`.
4. **`derive_scrypt` has no upper bound on n/r/p/dklen (decrypt-path DoS)** — `crypto.rs:38-55`, reached with attacker-controlled values at `keystore.rs:300-317`. A hostile keystore with `n=2^25, r=8` forces ~GBs of allocation on *load*. **Pre-existing** (faithfully preserved by the refactor); encrypt is fixed-parameter and safe. The shared function is the natural place for a ceiling.
5. **`PassphraseTooShort` says "characters" but measures bytes** — `error.rs:113` (measured at `passphrase.rs:167-175`). Byte-length is the security-correct measure; the message wording is cosmetic.

### Informational
`checksum_message` fail-open on short dk (currently unreachable — both call sites reject first); `EncryptInput` has no salt/iv uniqueness guard and `read()` hands back a plain `Vec` (real caller re-wraps in `Zeroizing` and draws fresh CSPRNG salt/iv/uuid — documentable footguns); `--passphrase-env` persists in the process environment (inherent to the feature; operator-doc note).

## K3 — CLI ceremony (commits `996152d`, `127cc5d`, `9f42c38`, `b3ba959`)

**Verdict: PASS (M-K3 met).** Test-backed gate properties: non-TTY `key new` → exit 2 before any generation; display-once ceremony via injectable `tty_writer` (production `/dev/tty`, fail-closed, no stderr fallback); mismatch → retry/abort → exit 4 with **zero** keystores written until re-entry matches; `recover` accepts 12–24 words from TTY or piped stdin, validate-first, bad word/checksum → exit 2; refuse-overwrite → exit 3 call-site; SIGINT → *k* complete keystores; exit map (Bip39→2, Hd→3, encrypt→3, Aborted→4) with `gen`'s Output→1 preserved; end-to-end `Zeroizing` incl. blst scalar scrub-on-drop; Debug redaction on config types.

### Medium
1. **`key recover` unknown-token echo** — see M1 (K3's instance; the review that calibrated it Medium and traced it to `architecture.md`). Fix before broad release.

### Low
2. **`--start-index + --count` overflow checked inside the write loop, not upfront** — `key_cmd.rs:322`; root cause `key_cli.rs::load_config`. `key recover --start-index 4294967295 --count 2` writes the index-`u32::MAX` keystore, then fails exit 2 with a file already persisted — a "config error / no side effects" code returned after real writes. Validate the sum in `load_config`.
3. **[Pre-existing]** **SIGINT handler armed before the `CancelToken` is initialized** — `main.rs:98-99`, `crates/core/src/cancel.rs:16`. A SIGINT in the first microseconds makes the handler run `get_or_init` → heap allocation inside a signal handler (not async-signal-safe); the safety comment at `main.rs:59-60` is false for that first invocation. Introduced in `e699229` (Rust restructure), serves all six subcommands. Trivial fix: call `global_cancel()` before `install_sigint_handler()`.
4. **[Shared with `gen`]** **`validate_output_dir` writability probe follows symlinks with a predictable name** — `key_cli.rs:338-346`. `.eth-deposit-probe-<pid>` opened with `File::create` (follows symlinks): in a world-writable output dir, a pre-planted symlink gets its target truncated with the user's privileges. No secret exposure; keystore writes themselves are `create_new`/`O_EXCL`-safe. Copied from `gen_cli` — fix both with `create_new(true).mode(0600)`; also stop ignoring `remove_file` errors.
5. **[By design]** **Filenames use HD path + whole-second timestamp** — `key_cmd.rs:360`. Two runs in the same second with overlapping indices collide; a same-second `key new` rerun runs the entire irreversible ceremony before failing at the write. Mirrors staking-deposit-cli convention; consider a uniqueness token or pre-ceremony collision check.

### Speculative / minor
SIGINT during an rpassword echo-off read leaves the terminal safe (RAII termios restore); edge: under non-default signal semantics EINTR could map to exit 2 instead of 4. Unbounded `read_to_string` on piped stdin and unbounded `--count` — minor for a local CLI. All write failures (not just overwrite) map to exit 3 — intentional, keeps `gen`'s Output→1.

## K5 + K4 — Withdrawal creds, E2E, docs (commits `b903a31`, `237b223`, `6d95cdf`, `84c7f12`)

**Verdict: PASS.** M-K5 fully met: `eip55_checksum` cryptographically correct (keccak-256 of lowercase hex, uppercase where nibble ≥ 8; reproduced against the 4 canonical EIP-55 spec vectors); `validate_eip55_address` rejects all-lowercase and any mismatch, never echoes a paste-ready corrected address; `eth1_withdrawal_credentials` exactly `0x01 ‖ 0×11 ‖ addr20`; the same creds flow into both `DepositMessage` and `DepositData`; require-choice gate fires before the banner, independent of `--dry-run`, catches empty string. K4-1 met: E2E chain byte-stable against a golden carrying real 0x01 creds (`0100…0914f1`, Hoodi fork, pubkeys match fixture). K4-2 met with one naming nit (finding 6).

### Low
1. **No pipeline-level defense-in-depth for withdrawal creds** — `gen_cmd.rs:108` re-checks the mainnet ack inside the pipeline, but nothing equivalent guards the more safety-critical creds, and `Entry::validate` (`deposit.rs:402-424`) doesn't check them. Two consequences: (a) the **zero address passes EIP-55** (all-digit → self-checksum), so a deliberate paste of `0x0000…0000` produces a 0x01 cred pointing at the burn address — permanent stake loss; (b) a future non-CLI caller constructing `GenConfig` with `[0u8;32]` would sign a placeholder deposit unopposed. Suggest rejecting all-zero creds in the pipeline (stays safe for a future 0x00 mode).
2. **Pre-signing banner omits the withdrawal address** — `gen_cli.rs:391-405`. The only checkpoint before signing shows network/pubkeys/count but not the destination — the one field where wrong-but-validly-checksummed = permanent loss. Echo the EIP-55 address + decoded creds.
3. **Exit code timing-dependent under heterogeneous per-pubkey failures** — `gen_cmd.rs:197-217` keeps the first-*received* non-cancellation error, not lowest-index; reported code varies by scheduling. Observability only; no output written on any error.
4. **Strict `0X`-prefix / bare-address rejection untested** — `signer/src/lib.rs:30-47`. Both correctly rejected today, but a refactor to case-insensitive prefix stripping would loosen strictness with no failing test.
5. **Dead OR-disjunct in two integration assertions** — `tests/gen.rs:353-356,391-394`: `contains("EIP-55 checksum mismatch") || contains("--withdrawal-address")` — the second disjunct is always true, so the test never pins *why* rejection happened. Drop it.
6. **`--from` asymmetry documented against the wrong command** — `README.md:86`, `USER-GUIDE.md:277`, `CHANGELOG.md:64-65` say "build/run's `--from`", but `--from` is build-only (run derives the sender from its signing key). Plan docs are more wrong (`project-plan.md:105`, `phase-k5.md` say "gen's `--from`"; gen has none). Direction and strict side are correct — naming fix only.

### Informational
7. **The 0x01 deposit roots have no independent oracle in CI** — the keygen golden is a self-generated regression lock; only the BIP-39/EIP-2333 seed is externally anchored (Trezor vector), and the existing SSZ anchor (`golden_smoke.rs`) uses 0x00 creds. Correctness rests on composition (anchored seed + content-agnostic SSZ HTR + hand-verified creds bytes + BLS verify-before-write). External parity comes from the manual M-K4 session — see below.
8. **"No `--entropy` flag" E2E assertion greps `--help`** — would miss a `.hide(true)` flag (none exist; grep confirmed). The real guarantee is architectural, and the byte-stable golden under real `OsEntropy` is the strongest determinism proof.
9. **Raw `--mnemonic-passphrase` in argv** — by design and properly documented (ps/history note in USER-GUIDE + CHANGELOG, env/prompt recommended, value Zeroizing-wrapped and Debug-redacted). Confirms the K4-2 criterion.
