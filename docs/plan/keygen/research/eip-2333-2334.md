# Research — EIP-2333 / EIP-2334 derivation via blst 0.3.16

**Question:** does `blst::min_pk::SecretKey::{derive_master_eip2333, derive_child_eip2333}`
(blst 0.3.16, already a workspace dep) implement **final** EIP-2333 — not the older
draft-irtf `KeyGen` — and reproduce the EIP's official test vectors byte-for-byte? And are
the EIP-2334 paths as simple as the overview assumes?

**Verdict: use blst as planned — empirically confirmed.** I compiled a throwaway crate
against `blst = "=0.3.16"` and ran all four official EIP-2333 vectors through
`derive_master_eip2333` + `derive_child_eip2333`; **every master and child SK matches the
EIP exactly** (output reproduced below). This validates the overview's "no hand-rolled
Lamport/HKDF tree" decision *and* proves the vector values transcribed here. EIP-2334 is a
4-level fixed path with a trivial index mapping and **no test vectors of its own** — we gate
it through the deposit pubkeys, not a standalone fixture.

## EIP-2333 algorithm (for reviewers; we do not re-implement it)

Source: [EIP-2333](https://eips.ethereum.org/EIPS/eip-2333). blst implements this in C
(`blst_derive_master_eip2333` / `blst_derive_child_eip2333`); the Rust file is a thin FFI
shim. We rely on the vectors, not a source read, to prove conformance (see verdict).

```
derive_master_SK(seed):            SK = HKDF_mod_r(seed)                 # seed is the BIP-39 seed
derive_child_SK(parent_SK, index): SK = HKDF_mod_r(parent_SK_to_lamport_PK(parent_SK, index))

HKDF_mod_r(IKM, key_info=""):      # L = 48, r = BLS12-381 curve order
    salt = "BLS-SIG-KEYGEN-SALT-"
    SK = 0
    while SK == 0:
        salt = SHA256(salt)                                    # salt is re-hashed each round
        PRK  = HKDF-Extract(salt, IKM || I2OSP(0, 1))
        OKM  = HKDF-Expand(PRK, key_info || I2OSP(L, 2), L)    # L = 48
        SK   = OS2IP(OKM) mod r
    return SK
```
`r = 52435875175126190479447740508185965837690552500527637822603658699938581184513`.
The child step builds a 255×2 Lamport key (`IKM_to_lamport_SK` uses HKDF-Expand with
`L = K*255 = 8160`, `K = 32`), compresses it with SHA256, and feeds that to `HKDF_mod_r`.
The lineage that changed between drafts is exactly `HKDF_mod_r` (the `I2OSP(0,1)` /
`I2OSP(L,2)` postfixes were added in the final EIP); the vector match below is what proves
blst is on the final version.

## blst 0.3.16 API — exact signatures and gotchas

From `~/.cargo/registry/src/*/blst-0.3.16/src/lib.rs`:

- `SecretKey::derive_master_eip2333(ikm: &[u8]) -> Result<SecretKey, BLST_ERROR>` (lib.rs:645).
  **It enforces a 32-byte minimum IKM in Rust before calling C:** `if ikm.len() < 32 { return
  Err(BLST_BAD_ENCODING) }` (lib.rs:648-649). Empirically confirmed: IKM lengths 0/16/31 all
  return `Err(BLST_BAD_ENCODING)`; length 32 succeeds. **This never bites us** — a BIP-39 seed
  is always 64 bytes — but K1-2 must still handle the `Result` (don't `unwrap` a caller-facing
  path).
- `SecretKey::derive_child_eip2333(&self, child_index: u32) -> SecretKey` (lib.rs:662).
  **Infallible** (returns `Self`, not `Result`) — the child step cannot fail.
- `SecretKey::to_bytes(&self) -> [u8; 32]` (lib.rs:747) — 32-byte **big-endian** scalar; this
  is what feeds `core::bls::new_signer(&[u8])` and the EIP-2335 keystore `secret`.
- `SecretKey::sk_to_pk(&self) -> PublicKey` (lib.rs:675); `PublicKey::to_bytes()`/`.compress()`
  gives the 48-byte compressed G1 pubkey. `core::bls::BlsSigner` already does exactly this
  (`crates/core/src/bls.rs:116-118`).
- Zeroization: blst's `SecretKey` zeroizes its scalar on `Drop` (noted at
  `crates/core/src/bls.rs:74`). The intermediate 32-byte `to_bytes()` buffer is **ours** to
  zeroize (per S-1); `new_signer` already copies-then-zeroizes its local (bls.rs:96-102).

## EIP-2334 paths

Source: [EIP-2334](https://eips.ethereum.org/EIPS/eip-2334). Path format
`m / purpose / coin_type / account / use` with fixed `purpose = 12381` (BLS12-381) and
`coin_type = 3600` (Ethereum BLS). Per validator index `i`:

- **withdrawal key:** `m/12381/3600/i/0`
- **signing key:** `m/12381/3600/i/0/0` — the 0th child of the withdrawal key.

The path maps to a sequence of `derive_child_eip2333` calls: start at the master SK, then
apply each slash-separated integer after `m` as a child index, in order. So the signing key
is `master → child(12381) → child(3600) → child(i) → child(0) → child(0)`; the withdrawal key
stops one level earlier (omit the final `child(0)`). **EIP-2334 ships no seed→SK test
vectors** — the WebFetch of the EIP confirms it defines structure only. Correctness is gated
downstream by the derived pubkeys matching ethstaker-deposit-cli (G2) and by our BLS-verified
deposit E2E (K4-1).

## Implications for our implementation

1. **K1-2 (`core::hd`) is a thin wrapper, not an algorithm.** Call blst directly (it is a
   `core` dep): `derive_master_eip2333(seed)?` then a fixed sequence of `derive_child_eip2333`.
   Model the path as a `[u32]` and fold `derive_child_eip2333` over it. No HKDF/Lamport code,
   no hkdf crate.
2. **Gate K1-2 with the four vectors above**, comparing `to_bytes()` hex. This is the M-K1
   milestone. The throwaway crate that produced the empirical run can be lifted into a unit
   test almost verbatim.
3. **Path model:** two paths per index — signing `[12381,3600,i,0,0]`, withdrawal
   `[12381,3600,i,0]`. Derive both; v1 only *uses* the signing key (the withdrawal pubkey is
   unused until 0x00 credentials land — see `withdrawal-credentials.md`), but deriving it is
   free and keeps the E2E honest.
4. **Handle the `Result` from `derive_master_eip2333`** even though a 64-byte seed can't trip
   the 32-byte guard; map any error to the crypto/keystore exit code (3). `derive_child` needs
   no error handling.
5. **Secrets:** wrap the `to_bytes()` output in `Zeroizing`; hand it to `new_signer` (which
   copies+zeroizes internally) and to the keystore encryptor, then drop. blst's own `SecretKey`
   objects self-zeroize on drop.
