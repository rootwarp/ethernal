# G4 — Batch-distinctness E2E regression test (2 pts · stream A · deps: —)

**Audit row flipped:** GHSA-c6rv-g6pj-r6qx / ETHSTAKER-6 (salt/IV reuse across a batch) — ✅ Mitigated → ✅
**Mitigated + regression-guarded** (gap-list item 4 closed) [SM-4].
**Lineage:** GHSA-c6rv-g6pj-r6qx / ETHSTAKER-6 — the catastrophic upstream class. Root cause upstream: a Python
"default argument evaluated once at import" footgun made every keystore in a batch **reuse the same scrypt salt
and AES IV**; with one operator password that yields an identical AES-128-CTR keystream across the batch, so
XOR of any two batch ciphertexts = XOR of the two 32-byte secret keys → secret-key recovery **without the
password** once multiple batch files leak.

**ethernal is already correct** — fresh CSPRNG `salt`/`iv`/`uuid` per keystore **inside** the loop
(`bins/ethernal/src/key_cmd.rs:344-351` BLS, `bins/ethernal/src/account_cmd.rs:351-358` EOA); the keystore
encrypt modules take already-drawn bytes and draw no RNG. **But** the only batch tests today use `FixedEntropy`,
where all keystores in a batch *intentionally* share salt/IV — so a regression reintroducing reuse would pass
the suite undetected. **G4 is the behavioral guard** that a future refactor cannot silently reintroduce the
reuse. **No product-code change.**

## Locked design decision + the binding amendment

- **D-G4 — `recover --count` on real OS entropy.** `new` needs a TTY (can't be pipe-driven), but salt/iv/uuid
  are drawn at **encrypt** time identically for `new` and `recover`, so `recover --count N` exercises the exact
  loop the GHSA class regressed in. Drive it with a fixed test mnemonic over stdin (the existing harness),
  **real OS entropy** (never `FixedEntropy`), and compare **raw JSON** fields (no decrypt).
- **⚠ G4-2 AMENDED (spec correction).** The EOA v3 keystore has **no `uuid` field — the top-level identifier is
  `id`** (`encrypt_v3.rs` emits `id: format_uuid_v4(...)`; `account_e2e.rs:343` already asserts `v["id"]`). The
  EOA distinctness assertion reads **`v["id"]`**, not `v["uuid"]`. The BLS v4 keystore *does* use top-level
  `uuid`.

## Exact JSON field paths (verified from `encrypt.rs` / `encrypt_v3.rs` source)

| Field | BLS v4 (`key_e2e`) — nested | EOA v3 (`account_e2e`) — flat |
|---|---|---|

## Test shape (identical logic, per path)

```
run_*_recover(dir, 3)                     // fixed mnemonic over stdin; real OS entropy for salt/iv/uuid
files = *_files(dir); assert files.len() == 3        // G4-3: fail loudly if fewer than requested
for f: read raw JSON (serde_json::from_slice) — DO NOT decrypt (byte compare only)
collect salt[], iv[], uuid_or_id[], identity[]
for each of salt / iv / uuid_or_id: assert HashSet::from(col).len() == 3   // pairwise-distinct, not adjacent
assert identity distinct too (pubkey+path for BLS, address for EOA) — proves 3 real validators, not 3 copies
```

Read **raw JSON only — no `Loader::load`**: distinctness is a byte comparison, and decrypting three
`N=262144` scrypt keystores per path would be wasted cost. Runtime is bounded — the only scrypt work is the
CLI's own encrypt of 3 files per path (6 total across both tests), vs the 4 the suite already pays at
`count = 2`.

## "Prove it bites" (G4-4 — comment only, NEVER committed)

Each test carries a comment documenting the local verification: temporarily replace the CLI's `OsEntropy` with
fixed bytes (or wire the `#[cfg(test)]` `FixedEntropy`) and rebuild, then run **only the two new tests** → the
salt/iv sets collapse to size 1 → the tests go **red**; revert. Scope this to the two new tests, not a third
full suite run. There is deliberately **no** entropy-injection flag on the CLI (enforced by
`key_recover_help_has_no_entropy_flag` / `account_recover_help_has_no_entropy_or_time_flag`, S-4), so the guard
cannot be toggled at runtime — and **must not gain a flag**. If a real-entropy batch path were somehow
unreachable, **escalate in the run summary rather than weakening the test to `FixedEntropy`**.
