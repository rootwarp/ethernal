## [F2-1] `FileSource`, the two `KeystoreError` variants, and `secret_file_arg`

**Points:** 2 · **Depends on:** F1-2 · **Discharges:** FR-6, FR-18, FR-19b, FR-23b, FR-26, FR-27

**Description.** The keystore-side boundary that streams A (F4) and B (F5) both consume, plus
the `-` guard all three streams call. After this issue, **F4-2 and F5-1 need nothing from F2
except this**.

**Implementation notes.**

1. **`FileSource`** in `crates/ethernal-keystore/src/passphrase.rs`, immediately after
   `EnvSource` (retained, M-5), shape from architecture §4:
   ```rust
   pub struct FileSource { path: PathBuf, warn_out: Mutex<Box<dyn Write + Send>>, warned: AtomicBool }
   ```
   - **The writer is injected, not `stderr()` internally** — `TermPromptSource`'s existing
     pattern (`passphrase.rs:72-79`), and what makes FR-21's warning counts deterministic.
   - **The warning latch:** `warned.swap(true)` selects `io::sink()` for every read after the
     first, so "exactly one WARNING" is a property of the type, not a coincidence of call order.
   - **FR-23b:** `read` builds its return with `Vec::with_capacity(s.len())` +
     `extend_from_slice` and drops the `Zeroizing<String>` immediately, so the mandatory boundary
     copy also never reallocates.
2. **Two variants, not seven** (D-6), in `crates/ethernal-keystore/src/error.rs`:
   `PassphraseFile(#[from] SecretFileError)` and `PassphraseFileEmpty { path }`. Wrapping the
   typed source keeps every failure *mode* `matches!`-able for FR-31 without seven
   near-identical variants. `PassphraseFileEmpty` mirrors `EnvVarEmpty` exactly (FR-18).
3. Re-export from `crates/ethernal-keystore/src/lib.rs:26` beside `EnvSource`.
4. **`secret_file_arg`** in `bins/ethernal/src/fs_util.rs`, beside `validate_output_dir` /
   `symlinked_output_dir` (architecture §8). Rejects `-` with exit 2. The message points at
   process substitution — `<(gpg -d pw.gpg)` — as the no-disk-file pattern and mentions
   `/dev/fd/N` only as the general escape hatch: **naming `/dev/stdin` alone would send an
   operator straight into the collision the rejection exists to avoid** (stdin is claimed by
   `tx sign --input -`, by `validator recover`'s piped mnemonic, and by `require_tty_for_new`).
5. The FR-19b worked example is a test in `bins/ethernal/src/keygen.rs`'s test module, where
   `MinLenPassphrase` lives (`keygen.rs:215-225`) — not in the keystore crate.

**Acceptance criteria.**
- [ ] **`FileSource: Sync` proven by a compile-time assertion** (`fn _assert_sync<T: Sync>() {}`
      instantiated with `FileSource`). F5's `&(dyn PassphraseSource + Sync)` bound
      (`gen_cmd.rs:143`) depends on it; discovering this in F5 is a cross-stream stall (R-10).
- [ ] **Warning latch:** five `read()` calls on **one** `FileSource` over a 0644 file produce
      **exactly one** line containing `file permissions` in the injected sink.
- [ ] An empty file (0 bytes) and a file holding only `"\n"` both → `PassphraseFileEmpty`.
- [ ] `MinLenPassphrase { inner: &FileSource, min: 8 }` over a file holding `1234567\n` →
      `PassphraseTooShort { min: 8, got: 7 }` — FR-19b's worked example, proven at the library
      level before any call site moves. (8 raw bytes → FR-8 → 7 → EIP-2335 normalize → 7.)
- [ ] `secret_file_arg("--passphrase-file", "-")` → exit 2; the message mentions `<(...)` process
      substitution and does **not** recommend `/dev/stdin` alone. A non-`-` value round-trips to
      the same `PathBuf`.
- [ ] `EnvSource` still present and re-exported (M-5); `rg -n '#\[deprecated' crates/ bins/`
      returns **zero** hits (D-10).
- [ ] No flag definition changed; `make lint && make test` green with **zero existing assertions
      modified**.

**Out of scope.** No call site moves (F4, F5). No signer work (F2-2). No `errors.rs` exit-code
assertions (F2-3).

## [F2-2] `new_local_signer_from_file` + `SignerError::KeyFile` + the FR-28 doc rewrite

**Points:** 1 · **Depends on:** F1-2 · **Discharges:** FR-7, FR-26, FR-28

**Description.** The signer-side boundary stream C (F6) consumes, and the correction of the doc
comments that currently name the environment as *the* secure source.

**Implementation notes.**

1. `crates/ethernal-signer/src/local.rs`, beside `new_local_signer_from_env` (retained):
   ```rust
   pub fn new_local_signer_from_file(path: &Path, warn_out: &mut dyn Write)
       -> Result<LocalSigner, SignerError>;
   ```
   Body: `read_secret_trimmed(path, warn_out).map_err(SignerError::KeyFile)?` then
   `new_local_signer_from_hex(&s)`, keeping the existing `map_err` that replaces the inner error
   with path-only context so no key material can leak.
2. `SignerError::KeyFile(SecretFileError)` + re-export from
   `crates/ethernal-signer/src/lib.rs:21`.
3. **No empty-file rule here** (architecture §5, §11 divergence 5): an empty file is not a
   distinct case — it fails `new_local_signer_from_hex`'s `stripped.len() != 64` check with
   "expected 32-byte (64 hex char) private key", which is S-A's *loud* property and the correct
   message.
4. **FR-28 doc rewrite** of `local.rs:70-73` ("MUST come from a secure source (environment
   variable…)") and `local.rs:85` ("Prefer `new_local_signer_from_env` in CLI code…"): the *key*
   still must never appear in argv; the *path* does, and the guarantee that buys is that a child
   process inherits a path, not a secret. `new_local_signer_from_file` becomes the
   recommendation for CLI code. **Ship without this and the code contradicts its own
   documentation.**
5. **`crates/ethernal-signer/tests/local_test.rs` contains zero `-env` flag occurrences and is
   still real work here** — it is sized by the *new API's* tests, not by flag hits.

**Acceptance criteria.**
- [ ] `new_local_signer_from_file` over a file holding a valid key with **no** trailing newline,
      with `\n`, with `\r\n`, and with surrounding spaces/tabs all produce the **same address**
      (FR-7 — hex contains no whitespace, so trimming is unambiguous).
- [ ] An **empty** file → the hex-length error, not a file-policy error (architecture §5).
- [ ] A not-found path → `SignerError::KeyFile(SecretFileError::NotFound { .. })`, and the
      rendered error contains the path and **not** the file's bytes — asserted with a distinctive
      sentinel written into a readable file for the permission-denied variant of the same check.
- [ ] `new_local_signer_from_env` still present and re-exported (M-5); no `#[deprecated]`.
- [ ] `rg -n 'environment variable' crates/ethernal-signer/src/local.rs` shows no line that
      presents env as the *required* or *preferred* secure source (FR-28).
- [ ] `make lint && make test` green with **zero existing assertions modified**.

**Out of scope.** The exit-code arm and its assertions (F2-3). Any `bins/` call site (F6).

## [F2-3] Exit-code mapping in `bins/ethernal/src/errors.rs`

**Points:** 1 · **Depends on:** F2-1, F2-2 · **Discharges:** FR-13, FR-27 (mapping half), D-7

**Description.** `errors.rs` has a `_ => 2` catch-all for keystore errors and a **`_ => 1`**
catch-all for signer errors. The keystore variants land correctly by accident; the signer variant
would silently become exit **1**. FR-13 requires 2. One explicit arm, and four assertions so none
of it is accidental.

**Implementation notes.**

1. The arm, **above** the exit-3 list (architecture §7):
   ```rust
   AppError::Signer(e) => match e.sentinel() {
       SignerError::UserRejected | SignerError::Cancelled => 4,
       // A key *file* configuration failure is a user error (FR-13), not a crypto
       // failure — unlike every other SignerError. Explicit, above the exit-3 list.
       SignerError::KeyFile(_) => 2,
       SignerError::SignerClosed | … => 3,
       _ => 1,
   },
   ```
2. One-line amendment to the module header's "3 — signer/crypto errors" comment recording the
   exception.
3. Assertions go beside the existing `EnvVarEmpty` assertion (`errors.rs:534` is the pattern to
   copy).

**Acceptance criteria.**
- [ ] `SignerError::KeyFile(_)` → **2**, asserted.
- [ ] **A sibling assertion pins `SignerError::InvalidKey` still → 3.** That second assertion is
      what holds `run::bad_key` green in F6 — a malformed key is a crypto failure, not a file
      failure.
- [ ] `KeystoreError::PassphraseFile(_)` → **2** and `KeystoreError::PassphraseFileEmpty { .. }`
      → **2**, both asserted explicitly rather than left to the `_ => 2` catch-all.
- [ ] The module-header comment names the `KeyFile` exception.
- [ ] `make lint && make test` green with **zero existing assertions modified**.

**Out of scope.** No call site constructs these yet. No CLI change.
